# ArchDev Skill

Date: 2026-09-21 (revised: grounded against `firstlanding/src/ts/archdev/src`)

Master skill for setting up and using ArchDev. `SKILL.md` holds the top-level
workflow (bootstrap → map → monitor). Each phase delegates to one reference
file plus a bootstrap script, following the existing `deprecated/` skill
layout (`SKILL.md` with `name:`/`description:` frontmatter, `references/`,
`scripts/bootstrap.sh` + `scripts/bootstrap.ps1`).

Proposed skill layout (new, alongside `deprecated/`):

```text
archdev/
  SKILL.md                  # top-level workflow, routes to references/
  references/
    bootstrap.md            # install CLI, login, verify
    map.md                  # repo mapping interview + taxonomy
    monitor.md              # self-check prompt + event reporting
  scripts/
    bootstrap.sh            # echo $archdev path; install/upgrade if missing
    bootstrap.ps1           # same for PowerShell
```

`scripts/bootstrap.*` mirrors the `deprecated/agents` contract: resolve the
absolute dir of the loaded `SKILL.md`, print the executable's absolute path
on stdout, install/upgrade when `agents`/provider commands are missing, and
do NOT log in or install a daemon. Skill install target (repo vs global) is
unchanged: repo-installed skill scopes to that repo; global applies to any.

## 1. Bootstrap

Goal: CLI installed at current version AND user logged in. Reference:
`references/bootstrap.md`.

Concrete steps (verified against the CLI in firstlanding):

0. First run `"$archdev" repo status --json` (new, §4). It reports every
   check below as ok/missing with its remediation — follow them top to
   bottom and re-run until all ok. Steps 1–4 are what `status` checks.
1. Resolve CLI: `"${archdev}"` from `scripts/bootstrap.sh`
   (`set archdev (bash .../bootstrap.sh)` in Fish,
   `& $archdev` in PowerShell).
2. Version/health: `"$archdev" --version`, then `"$archdev" auth status`.
   If unauthenticated: `"$archdev" auth login [email]` (browser,
   copy/paste, or PAT). Keep the browser/device-code flow running while the
   human signs in.
3. Model access is separate from ArchDev login. Check
   `"$archdev" settings provider status` independently of `auth status`.
   For agent-only onboarding without Jobs/daemon/private remotes, run
   `"$archdev" agents setup [--provider openai|xai|archdev ...]` from the
   target repo. Full onboarding is `"$archdev" setup` (`--skills` for
   skills-only, `--no-skills` to skip the skills installer).
4. Validate repo wiring with `"$archdev" check` (validates config without
   executing). Success criteria: `auth status` ok, `check` clean.

Bootstrap must NOT run full `archdev setup` merely to inspect state, and
must use `--help` from the installed version rather than assuming new
commands exist.

## 2. Map

Goal: opt a repo into ArchDev via a checked-in `archdev.json`, plus a
resource taxonomy that drives detection prompts. Reference:
`references/map.md`.

### 2a. Init

1. Look for `archdev.json` in the repo root. If present, keep it and
   continue to mapping.
2. If absent, run `"$archdev" init [--name <unique-private-repo-name>]`
   (equivalent to `"$archdev" jobs repo enable`). This creates `archdev.json`
   with `local.project_id` / `local.repo_name` (cf. firstlanding's own
   `archdev.json`: `local: { project_id, repo_name }`).
3. Personal/model overrides belong in gitignored `archdev.local.json`
   (`modelAliases`, `factory.model`, provider accounts), never in the
   checked-in file. Re-run `"$archdev" check` after editing.

### 2b. Mapping interview

The agent maps how the repo works and how the user works. Persist findings
under a new additive top-level `archdev.json` key, `activity` (new;
validated by `check`, ignored by older CLIs):

```jsonc
{
  // ... existing keys (factory, publish, tasks, pipelines, ...)
  // Arrays throughout: repos routinely use several of everything at once.
  "activity": {
    "version": 1,
    "resources": {
      "plan":   { "origins": ["skill", "manual"],
                  "environments": ["local", "remote"],
                  "style": "<free text>",
                  "locations": ["docs/plans/"],
                  "detection": "<prompt>" },
      "task":   { "origins": ["skill", "manual"],
                  "systems": ["archdev", "linear"],
                  "environments": ["local", "remote"],
                  "style": "<free text, incl. per-system notes>",
                  "detection": "<prompt>" },
      "agent":  { "harnesses": ["claude", "codex"],
                  "environments": ["local", "remote"],
                  "detection": "<prompt>" },
      "commit": { "detection": "<prompt>" },
      "pr":     { "providers": ["github"],
                  "detection": "<prompt>" },
      "repo":   { "vcs": "git",
                  "worktrees": ["<where worktrees live>"],
                  "detection": "<prompt>" }
    }
  }
}
```

`origins`/`environments`/`systems`/`harnesses`/`providers`/`locations`/
`worktrees` are all string arrays (empty = unknown, filled by the
interview). `vcs` is a single string (`git|jj|sapling|hg|svn|…`, free text
allowed). `detection` is required per resource — it is what the monitor
phase consumes. `check` enforces: arrays contain non-empty strings,
`detection` non-empty, `vcs` non-empty.

Known `task.systems` vocabulary (open list — record what the repo actually
uses, not just what ArchDev automates):

| System | Typical env | How the agent detects it |
|---|---|---|
| `archdev` | local | `tasks.backend: archdev`, `archdev tasks list` works |
| `beads` | local | `tasks.backend: beads`, `.beads/` dir |
| `github` | remote | issues/projects; `gh` CLI, origin remote |
| `linear` | remote | `linear` MCP/CLI, issue IDs (`ENG-123`), app links |
| `jira` | remote | `jira` CLI/MCP, issue keys (`PROJ-123`) |
| `asana` | remote | app links, MCP |
| `trello` | remote | board links |
| `notion` | remote | database links |
| `clickup` | remote | task links |
| `azure-boards` | remote | `AB#123`, ADO links |
| `youtrack` | remote | issue IDs, links |
| `todoist` | local/remote | CLI/app |
| `markdown` | local | `TODO.md`, `tasks/` dir, checkboxes in docs |
| `manual` | — | user assigns work in chat; no tracker |

Only `archdev|beads|github` are CLI-verifiable (`ARCHDEV_TASK_BACKENDS`,
`tasks list|show`); the rest are observed from trajectories, links, and
IDs, and noted in `style` with per-system detail (e.g. "eng planning in
Linear, agent micro-tasks in beads"). Same rule for `agent.harnesses` —
reuse the room-exhaust vocabulary
(`claude|codex|cursor|gemini|copilot|opencode|grok|archdev`) plus free
text — and `pr.providers` (`github|gitlab|bitbucket|forgejo|azure`, …).

Interview checklist (sources in parentheses):

- Plan: where do plans/docs go (`docs/plans/` in firstlanding-style repos)?
  What skill produces them? What style/format?
- Code: what harness, what cloud agents, what orchestrator (Factory vs
  one-off `agents run`)? Tasks optional for ordinary sessions — do not
  create Tasks/DAGs just to start an agent.
- Review: GitHub PRs (`inspect`/`reviews` workflows + `publish`), direct
  push, or local-only?
- Instruction style: read past trajectories — tasks, chat prompts, or
  session pulls? Record every tracker in `task.systems` (vocabulary table above —
  Linear/Jira/etc. included), not just `tasks.backend` (`archdev|beads|
  github`; firstlanding constant `ARCHDEV_TASK_BACKENDS`). Use
  `"$archdev" tasks list|show` to confirm a live backend vs a stated one;
  remote trackers are confirmed from IDs/links in trajectories.
- Each resource gets: what it is for, how the repo uses it, where it is
  stored, and a `detection` prompt so a model can recognize the event live.

### 2c. Events (closed vocabulary)

The monitor phase may emit ONLY these events, all transported as room
messages via `archdev log` (§4). `agent.message` is the unstructured
catch-all (plain text, no attachment); every other event is structured
(extract payload attached as `structured_data`). Each structured event maps
to an `extract` subject/extractor (only `pr.review-annotations` on subject
`pr` exists today; the rest are new extractors to build — see §4):

| Event | Subject ref for `extract run` | Notes |
|---|---|---|
| `agent.message` | — (unstructured, no extractor) | free-text note, e.g. steering remarks, ambiguous observations |
| `plan.created` / `plan.started` / `plan.updated` | plan path | payload: location URI, title, description |
| `task.created` / `task.started` / `task.updated` / `task.closed` | task id | `tasks show <id>` is the subject snapshot |
| `agent.session_started` / `agent.session_stopped` / `agent.steered` | session id | stopping points monitored |
| `commit.created` / `commit.pushed` | commit sha | (`commit.updated` dropped: commits are immutable; amend = new sha) |
| `pr.created` / `pr.updated` / `pr.closed` | PR number | resolves via GitHub origin remote, as `pr.review-annotations` does |

Extractor ids follow the existing dotted convention `subject.name` with
optional `@variant` (e.g. `plan.created`, `task.lifecycle`,
`agent.session`, `commit.observed`, `pr.lifecycle`). Runners
(`llm:<model>`, `file:<path>`, `deterministic`) and sinks
(`object`, `file:<dir>/`, `stdout`) are reused unchanged.

### 2d. Install hooks (final map step)

Mapping ends with start + stop hooks installed via the existing harness
hook system (`reviews/hooks/`, §4). Both are installed during map — not
deferred to monitor — so session coverage starts immediately:

```text
archdev repo hook setup [--harness claude|codex|grok] [--force] [--uninstall]
```

- Start hook → `archdev repo hook start --harness <h>`: emits
  `agent.session_started` and injects the `repo monitor bootstrap`
  self-check block as session context, so every session starts mapped.
- Stop hook → `archdev repo hook stop --harness <h>`: stopping-point
  self-check reminder; the agent reports hits via `archdev log`.
- `--uninstall` removes them; without `--harness`, install covers every
  installed harness (config-dir presence = installed) and warns when none
  is found — pass `--harness <name>` to install anyway.
- Harnesses outside `claude|codex|grok`: the agent hand-authors start/stop
  entries invoking the same two `repo hook` commands, so promotion
  (§4) stays uniform. `repo status` verifies both hooks per harness.

## 3. Monitor

Goal: validate the taxonomy against real sessions before building
infrastructure. Reference: `references/monitor.md`.

Phase 1 is model-as-sensor — no daemon, no log tailing, no file watchers:

1. Load skill → verify bootstrap (`auth status`) and repo state (`check`).
2. Emit the self-check block with the new CLI command
   `"$archdev" repo monitor bootstrap` (new; prints Markdown). Block
   contents:
   - active resource list with `detection` prompts (from `activity`),
   - allowed event names (§2c, closed list),
   - per-event extraction schema (from `archdev extract context <id> <ref>`),
   - the exact report commands: `archdev log <text>` for free-text notes
     (event `agent.message`), `archdev log --event <type> --payload-file`
     for schema-validated hits.
3. The agent self-checks at stopping points and reports hits via the CLI.
4. Promotion rule: once an event fires reliably in real sessions, promote
   high-signal ones (`commit.*`, `pr.*`) to real hooks/polling and remove
   them from the self-check block to save model attention.

`archdev minimap ping` (session snapshot) stays as-is and is NOT the event
transport.

### Coexistence with rooms and minimap (do not break either)

Copied from the rooms skill and the minimap publisher — these are
invariants, not suggestions:

- **Presence belongs to minimap.** Session snapshots (`minimap ping`,
  publisher heartbeats, `observeSession`) are the only presence writers.
  Activity events never carry minimap identity fields (`producer_id`,
  `incarnation_id`, `subject_id`, `sequence`), never use
  `stream: "archdev-minimap"`, never use schema config
  `archdev-minimap-v1`, and never set `type: "exhaust"` on log posts
  (minimap's type). Minimap consumers filter on stream/schema and must
  never see an activity event, and vice versa. The hook-start handler
  emits an activity event only — it never synthesizes presence.
- **Activity metadata carries its own stream.** Log posts set
  `metadata.stream: "archdev-activity"` alongside `post_type: "log"`
  and `event:` (new — mirrors minimap's `stream: "archdev-minimap"`),
  so activity is filterable as a stream without touching minimap's.
- **Rooms lifecycle posts stay.** `rooms start|lesson|done|…` are team
  exhaust (human-readable, quality-gated); activity events are machine
  signals. The monitor phase adds the latter without replacing the
  former: substantial work still gets a rooms `start`/`done`, and
  `agent.session_started` is NOT a substitute for `rooms start`.
- **Delivery rules (from `rooms connect`).** Verify the post result
  (`messageId`); a connection/auth failure before queueing means the
  event was NOT recorded — report and retry after login/connectivity is
  restored. A successful queue response must never be retried by the
  caller. Only the top-level session posts (one synthesized result);
  subagents search and read but never post. Failed posts are reported
  with their reason, never as delivered.
- **Idempotency follow-up.** The minimap publisher dedups with
  `idempotency_key`; log posts have none yet, so a hook-start retry or
  an agent retry can double-post `session_started`. Adding
  `idempotency_key` (event + session + seq) to log posts is tracked as
  checklist item A12.

## 4. CLI additions (in firstlanding `src/ts/archdev/src`)

New `repo` namespace, disjoint from `jobs`/daemon commands. None of these
exist today (`repo` only appears as `jobs repo enable|disable|sync|submit`):

```text
archdev repo status [--json]                 # one-shot readiness probe (see below)
archdev repo init [--name <name>]            # alias of `init` / `jobs repo enable`
archdev repo map init [--force]              # scaffold activity skeleton in archdev.json
archdev repo map bootstrap                   # print mapping interview guide (Markdown)
archdev repo monitor bootstrap               # print self-check block for activity config
archdev repo hook setup|start|stop          # harness start/stop hooks (see below)
```

### `archdev repo status`: the easy button

The skill's bootstrap and repo-setup steps collapse into one call. `status`
aggregates checks the CLI already implements and reports each as
ok/missing with the exact remediation command; `--json` emits a machine
readable array the agent branches on:

| Check | Source | Remediation when missing |
|---|---|---|
| CLI version current | `--version` vs update check | reinstall via Homebrew/installer |
| ArchDev login | `auth status` (`tryResolveAuth`) | `archdev auth login [email]` |
| Model access | `settings provider status` | `archdev agents setup [--provider …]` |
| Repo initialized | `isProjectInitialized` (`local-daemon/init.ts`: `archdev.json` + `local.project_id`/`repo_name` + daemon DB registration + receive hook) | `archdev repo init [--name …]` |
| `activity` taxonomy mapped | `activity.version == 1`, every resource has a non-empty `detection` prompt | `archdev repo map init` then interview |
| `activity` valid | same validators `check` runs, extended with the activity schema | fix reported keys |
| Start + stop hooks installed | `repo hook` groups present per detected harness | `archdev repo hook setup [--harness …]` or hand-authored equivalent |

Skill bootstrap becomes: run `repo status --json` → execute remediations
top to bottom → re-run until all ok. No other probing commands needed.

### `archdev repo map init`: scaffold, don't hand-author

`map init` writes the `activity` skeleton so the agent fills blanks instead
of inventing JSON structure. Prefill from detected state, leave `detection`
empty for the interview:

- `task.systems` seeded from the resolved `tasks.backend`
  (`archdev|beads|github`, `ARCHDEV_TASK_BACKENDS`); append tracker IDs
  observed in docs/trajectories (`linear`, `jira`, …) for the interview to
  confirm. `task.locations` from backend (e.g. `.beads/` when beads).
- `plan.locations` from common dirs found in the repo (`docs/plans/`,
  `plans/`, `specs/` — whichever exist).
- `pr.providers: ["github"]` when `origin` parses as GitHub (same
  `parseRemote` helper the PR extractor uses); `repo.vcs`/`worktrees`
  from VCS topology (`git rev-parse`, `jj root`, …).
- Refuses to overwrite a filled taxonomy without `--force`; merges missing
  keys otherwise. Afterwards `archdev check` (extended with the activity
  schema) must pass.

### Skill distribution

The skill ships in the published skills manifest of `ArchAstro/archdev`
so the existing installers pick it up with no new mechanism: `archdev
setup --skills` (global, detected tools) or `npx skills add
ArchAstro/archdev` (interactive chooser) — same path `setup-skills.ts`
already uses. Repo-scoped install remains a checkout of this repo's
`archdev/` skill dir.

### `archdev log`: two event kinds, one transport

Both unstructured and structured events post to the org-room thread via the
existing message endpoint (`POST /api/v1/threads/{threadId}/messages`).
That body already supports what we need — precedent: `minimap/publisher.ts`
posts `{ content, type: "exhaust", idempotency_key, metadata: { stream,
version, kind }, attachments: [{ type: "structured_data", schema_config,
data }] }`, and `room-exhaust.ts` posts `structured_data` attachments under
schema config `archdev-rooms-exhaust-v1`. `room-outbox.ts` persists the same
attachment shape, so structured events survive offline enqueue.

```text
archdev log [message...] [--event <type>] [--json]
  # unstructured (default --event agent.message): posts
  # { content, user, metadata: { source: archdev, post_type: log, event } }

archdev log --event <type> --payload-file <path> [--message <text>] [--json]
  # structured: same post PLUS
  # attachments: [{ type: "structured_data",
  #                  schema_config: <extractor schema config>, data: <payload> }]
  # --message supplies the human-readable content line (defaults to a
  # one-line "<event>" summary); --payload-file is the stored extraction
  # envelope value (see flow below)
```

Implementation notes (`org-log.ts`):

- Loosen `<message...>` to `[message...]` so the structured form needs no
  positional text. `--event` defaults to `agent.message`; `--payload-file`
  requires `--event` other than `agent.message`.
- Today's `metadata: { source, post_type: "log" }` gains `event: <type>` in
  both forms so consumers filter on one key. `post_type: "log"` is kept for
  backward compatibility with existing room readers.
- Structured flow reuses the extract engine, not the room poster, for
  validation: agent runs `extract context <id> <ref>` → authors JSON →
  `extract run <id> <ref> --runner file:<path>` (validates against the
  extractor zod schema and stores the envelope) → `log --event <type>
  --payload-file <envelope-value-file>`. `log` re-validates the file
  against the extractor schema via the registry before attaching, and sets
  `schema_config` to that extractor's deployed config key (same pattern as
  `MINIMAP_SCHEMA_CONFIG` / `ROOM_EXHAUST_SCHEMA_CONFIG`).
- No `repo log-event` command: the variadic collision is solved by options,
  keeping one `log` surface for agents to learn.

New extractors ship as `ExtractorEntry` rows in `extract/commands.ts`
alongside `pr.review-annotations`, one subject per `extract/subjects/`
(`plan.ts`, `task.ts`, `agent-session.ts`, `commit.ts`) plus `pr-lifecycle`
next to `pr.ts`. `archdev extract list|context|run|show|replay|guide`
works for all of them with no command changes.

### Hooks: add `Start`, grow the stub

Today `HOOK_EVENTS = ["Stop"]`, installed by `inspect setup` and handled
by `inspect hook <name>` (a stub: it normalizes harness/session/payload
and exits 0 — a failing or stalling hook degrades its harness, so it never
exits nonzero and stays silent unless asked). Changes:

1. New `repo hook` namespace owning the whole surface:
   `archdev repo hook setup [--harness …] [--force] [--uninstall]`
   (`install` kept as an alias) plus the two entrypoints harnesses
   invoke, `archdev repo hook start` and `archdev repo hook stop`.
   `HOOK_EVENTS = ["Start", "Stop"]`,
   `HOOK_NAMES = { Start: "start", Stop: "stop" }`; setup writes both
   groups per harness under the new `archdev repo hook` command prefix
   (same merge rules, same 30s timeout).
   Migration: `isArchdevGroup` keeps recognizing the legacy
   `archdev inspect hook` prefix so `repo hook setup` replaces (and
   `--uninstall` removes) hooks the old `inspect setup` wrote.
   `inspect setup` / `inspect hook stop` remain as compat aliases during
   transition; the skill and all new docs use `repo hook` only.
2. `hook start` behavior: resolve repo + `activity` taxonomy, emit
   `agent.session_started` via the log path (§4 `log`), and print the
   `repo monitor bootstrap` block to stdout so the harness injects it as
   session context. No session context (repo unmapped) → print nothing,
   exit 0: the skill interview remains the mapping path, not the hook.
3. `hook stop` behavior, phased. Phase 1: print the stopping-point
   self-check reminder (resource list + allowed events); the agent does
   the check and reports. Phase 2 (promotion, §3): the handler itself
   emits deterministic high-signal events (`commit.*`, `pr.*` via
   subject resolution + extract + log) and stays silent otherwise, so
   model attention is spent only on events still needing judgment.
4. Harness without a start/session-start event: skip `Start` for it in
   setup output; `agent.session_started` falls back to the skill's
   bootstrap step (`repo status` → `log --event agent.session_started`).

## 6. Testing & benchmarks

Two levels. Unit tests prove the commands work; evals prove the skill
works. Conventions borrowed from the evals program
(`docs/plans/2026-09-08-evals-program-catalog-benchmarks-stripe-design.md`,
`evals/runner/`, `evals/coding/tasks/codebase-mapper.yaml`).

### 6a. Unit/integration (firstlanding, vitest `__tests__/`)

One test file per checklist item, following the existing suites
(`room-exhaust.test.ts`, `room-outbox.test.ts`, hook merge tests):

- activity schema: valid/invalid taxonomies, empty-`detection` rejected,
  unknown keys rejected, old-CLI-ignores-new-key compatibility.
- `repo status`: each row ok/missing, remediation strings, `--json`
  shape, nonzero exit on failure.
- `map init`: prefill from fixture repos (backend, dirs, origin, VCS),
  merge-without-`--force`, overwrite refusal, `check` green after.
- `log`: metadata `event` in both forms, `structured_data` attachment
  shape + `schema_config`, registry re-validation failure on bad payload,
  `post_type: "log"` preserved.
- hooks: merge/replace/uninstall for both the new `repo hook` and legacy
  `inspect hook` prefixes; `hook start` emits + prints; silent-0 on
  unmapped repos.

### 6b. Behavioral evals (`evals/coding/tasks/`, `evals/runner/`)

New YAML tasks beside `codebase-mapper.yaml`, same anatomy (`agent`,
`setup.world`, `run.sources` with prompts + `max_turns`,
`outcome.pass_fail` with deterministic needles + light LLM judge).
Fixture pattern applies verbatim: the ground truth (expected events,
expected taxonomy) sits beside the agent's workdir and is never
materialized into it.

- `skill-map.yaml`: agent with the skill maps a fixture repo
  (seeded with Linear IDs, `docs/plans/`, beads backend, GitHub origin).
  Needles (identifier-shaped, paraphrase-proof): `"activity"`,
  `"detection"`, `"linear"`, `"docs/plans/"`, `"beads"`.
  LLM-quality gate: every resource has an accurate, repo-specific
  `detection` prompt; no invented trackers. Evidence: resulting
  `archdev.json` + `repo status --json` all-ok.
- `skill-monitor.yaml`: agent replays a fixture session transcript with
  known ground-truth events (plan created, task closed, commit pushed,
  plus one ambiguous chatter that must stay `agent.message` or unlogged).
  Needles: emitted event names in order. LLM-quality gate: no hallucinated
  events, structured payloads validate against their extractor schemas.
  Evidence: room outbox entries (content + metadata + attachments).
- `skill-hooks.yaml`: after `repo hook setup`, start hook fires on a new
  session (context block injected, `session_started` logged) and stop
  hook fires at end. Needles: `"session_started"`, hook command strings
  in harness config. Deterministic — no LLM judge needed.

Benchmark discipline (from the evals program):

- A/B via `run_ab.ts` for every comparison that matters: skill vs
  no-skill mapping quality, hook-reminder vs no-reminder event recall,
  old vs new CLI on the same fixture (regression gate on CLI changes).
- Aggregate with `aggregate_runs.ts` (Wilson intervals, ported from
  `benchmarks/harness/stats.py`); compare page checks comparability —
  same fixture digest, same agent, same repeats — before pooling.
- Fixtures + answer keys are versioned data (M4.5 catalog rule:
  hand-authored dirs, generic validation test, digest lock). A second
  scenario is a catalog-style addition, not harness work.
- Target stays local/staging fixtures. No production evaluation, no
  real org rooms — assertions run against the outbox and produced
  artifacts, mirroring the pilot in B4 before it graduates to live rooms.
